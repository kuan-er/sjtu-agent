# Agent token 量级与预算取值建议（2026 下半年）

> **观测日 2026-09-24**｜本机实测 + 官方价目表交叉核对｜面向本仓库（sjtu-agent）的取值建议
> 证据分级：**[实测]** 本机数据/本次测量；**[官方]** 厂商官方页面；**[外部]** 第三方实测或社区报告；**[建议]** 我的取值主张
> 配套三份子调研：`ai-agent-token-magnitudes-h2-2026.md`（模型规格与价格）、`harness-context-practice-2026H2.md`（各家上下文管理实作）、`agent-token-survey-2026H2.md`（外部实测的 token 消耗）

## 0. 先给结论

1. **单次调用的上下文量级是按「十万」计的**：本机 3,076 次真实调用实测 —— 中位 **28.9 万 tokens**、p90 **58.1 万**、p99 **69.2 万**、峰值 **71.4 万** [实测]。也就是说 1M 窗口不是"用不满的余量"，而是被稳定用到 **30%~70%**。
2. **但每次新增输入只有中位 282 tokens**（占上下文 0.04%）[实测]：成本结构不是"聊得多"，而是**同一条稳定前缀被反复重发**，因此**缓存命中率才是真正的成本开关**，不是上下文长度本身。
3. **harness 固定开销 ~2.6 万 tokens/次**（DSH，其中工具 schema 约 2.2 万）[实测]；本仓库 sjtu-agent 实测 **~1.74 万**（系统提示 1.28 万字符 + 76 个工具 schema 3.78 万字符，按实测 2.9 字符/token 折算）[实测]。
4. **窗口与折叠阈值别按老经验拍**：2026 各家实现普遍落在**窗口的 80%~95%** 才压缩（Claude Code 1M 模型 ~967K、Codex 实际等到可用窗口 94.74%、dsh `thresholdRatio=0.8`）[外部]。本仓库当前 `SESSION_QUALITY_BUDGET = 256_000`，在 1M 窗口下只用了 25%，**远早于外部同类实现**——而"太早折叠"正是"限制窗口太小容易截断"的另一种形态。
5. **不要信框架自带的 cost 字段**：本机账本把 `deepseek-flash` 按 **V4-Pro 价目**计价，比官方 Flash 价恒定高 **6.67×** [实测]（见 §4）。自己按官方价目表算。

## 1. 本机实测：一次 agent 调用到底多大

数据源：`~/.dsh/dsh-usage/usage-ledger.json`（8 天日账）+ `~/.dsh/sessions/**/session.v3.jsonl`（30 份会话、3,076 次带用量的模型调用、24 份含调用）。**这是本机真实负载，不是基准测试。**

| 指标（每次模型调用） | min | p50 | p90 | p99 | max | 均值 |
|---|---|---|---|---|---|---|
| 上下文总量（input + cacheRead） | 5,790 | **288,761** | 581,409 | 691,842 | **714,318** | 312,219 |
| 其中未命中缓存的新增输入 | 21 | 282 | 2,168 | 15,063 | 305,487 | 1,358 |
| 输出 tokens | 41 | 497 | 1,680 | 5,724 | 88,226 | 862 |
| 其中思考 tokens | 0 | 71 | 765 | 4,104 | 83,056 | 344 |

| 指标（每次会话 / 工具结果） | 数值 |
|---|---|
| 每会话模型调用次数 | p50 41，p90 426，max 667 |
| 会话首次调用上下文（≈ harness 固定开销 + 首条用户消息） | p50 **25,630**，p90 27,327，max 27,402 |
| 单条工具结果字符数 | p50 448，p90 4,239，p99 22,635，max 51,486 |
| 缓存命中占上下文比例（总量口径） | **99.6%** |
| 思考占输出比例（总量口径） | **39.9%** |

### 固定开销分解（字符 → token 按实测 2.9 字符/token）

| 组成 | DSH（本机运行时） | sjtu-agent（本仓库） |
|---|---|---|
| 系统提示词 | p50 11,493 字符 ≈ 4.0K tokens | 12,812 字符 ≈ 4.4K tokens |
| 工具 schema | p50 63,604 字符 ≈ 21.9K tokens | 37,768 字符（76 个工具）≈ 13.0K tokens |
| 合计固定开销 | **≈ 25.6K tokens** | **≈ 17.4K tokens** |
| 最贵的单个工具 schema | — | `add_mcp_server` 1,579 字符、`create_skill` 1,208、`configure_canvas_monitor` 1,207 |

> 对照外部：54 工具时 schema 占每次请求 **83.1%**、真实对话仅 0.6%（hermes #67273）[外部]；一句 "hello" → 22,300 tokens 的 prompt（qwen-code #6097）[外部]。本机 25.6K 与该量级一致。

## 2. 上下文是怎么涨上去的（以及折叠发生在哪里）

跨会话聚合的中位上下文（按会话内 step）：

| step | 1 | 5 | 10 | 20 | 30 | 40 | 60 |
|---|---|---|---|---|---|---|---|
| 中位上下文 | 27.3K | 60.7K | 111.1K | 144.6K | 284.5K | 320.1K | 303.2K |
| 最大上下文 | 704K | 710K | 714K | 651K | 662K | 677K | 460K |

- **前 30 步近似线性：约 +8.9K tokens/步**（每次工具调用 + 结果 + 助手消息）[实测]；外部同口径是 +1,719/+1,838 tokens/步（TraceLab，Claude Code + Codex）[外部]，本机明显更高（本机工具结果 p90 4.2K 字符）。
- 曲线在第 16、44~45、59~60 步出现**回落**（如 405.3K → 270.6K），即**折叠/压缩事件**：幅度约 −130K tokens [实测]。
- 结论：**折叠阈值决定"多久折一次"**。本仓库 256K 预算会在 step 8~10 附近首次触发（中位 111K 时尚不触发，20 步 145K，30 步 285K → 触发点落在 step 25~30 之间），而外部实现要到 800K+。

## 3. 成本：官方价目 vs 账本价

按官方价目（DeepSeek V4.1-Flash：输入 $0.15/1M、缓存命中 $0.003/1M、输出 $0.60/1M，谷时）[官方]，本机 8 天负载：

| 口径 | 计算 | 结果 |
|---|---|---|
| 实际计费口径（含缓存） | 新增输入 2.75M×$0.15 + 缓存 890.7M×$0.003 + 输出 2.35M×$0.60 | **≈ $4.49 / 8 天** |
| 反事实：无缓存（每次重发全量上下文） | 893.4M×$0.15 + 2.35M×$0.60 | **≈ $135.4 / 8 天** |
| 账本自报 | 账本 `cost` 字段合计 | $30.17 |

两个结论：
- **缓存带来 ~30× 的成本差**（$4.49 vs $135.4）[实测+官方]。保持稳定前缀（会话中不换模型、不增删工具、易变内容后置）不是优化技巧，是成本前提。
- **账本自报 $30.17 与官方价核算的 $4.49 差 6.7 倍**：逐日比对显示账本**按 V4-Pro 价目**计价（V4-Pro 缓存读 $0.022/1M vs Flash $0.003/1M），8 天比值恒为 6.67×、与官方 V4-Pro 价核算比为 1.03~1.52× [实测+官方]。**用框架自带的 cost 字段做决策会系统性高估（或低估）成本。**

## 5. 对 sjtu-agent 的取值建议

| # | 项目 | 现状 | 建议 | 依据 |
|---|---|---|---|---|
| 1 | 折叠预算 `SESSION_QUALITY_BUDGET` | `256_000`（但 `context.py` 模块 docstring 仍写 64K，**不一致**） | 先修 docstring；预算提到 **窗口的 ~50%（1M 窗口 → 500K）**并埋点观察，再决定是否上探 0.7~0.8×；**不要停在 25%** | 外部实现 80%~95% [外部]；本机 p50 已达 289K [实测]，256K 会频繁触发；"70% 利用率崩塌"被点名无方法学 [外部]，不能当依据 |
| 2 | 输出上限 `max_tokens=4096`（runner/vision/news 多处） | 4096 | 提到 **32K~64K**（或按模型能力配置）；推理模型必须给思考留足预算 | 官方：Flash 最大输出 **384K** [官方]；本机思考占输出 40%、外部 Opus 可达 98% [实测/外部]；本仓库日报曾因 4096 截断推理内容（#201） |
| 3 | 工具 schema 开销 | 76 个工具 / 37.8K 字符 ≈ 13K tokens（占固定开销 75%） | (a) **会话中工具集保持稳定**；(b) 按意图分组懒加载（邮件/Canvas/食堂/提醒各自成组）；(c) 精简描述与参数说明 | Cursor 官方：静态工具描述 −60%、MCP 动态化 −46.9% 会话 token、总成本 −7% [官方]；反例：小 skill 上按需加载反而 +48.4% [外部] → 要按组分，别按单个工具 |
| 4 | 缓存纪律 | 折叠/清理是确定性操作（已做对） | 补齐：**不在会话中增删工具、不切模型**；时间戳/随机 ID 等易变内容一律后置到稳定前缀之后 | Claude Code 硬规矩 + dsh 同款设计 [外部/源码]；§3 的 30× 差价 [实测] |
| 5 | 工具结果内联上限 | `fetch_url` 8,000 字符截断 | 内联上限 **~10K 字符**，超出**落盘 + 回路径与预览**；优先"剪枝旧结果→重新计量→不够再折叠"的顺序 | 本机工具结果 p99 22.6K 字符、max 51.5K [实测]；Codex 按 10KB 字节截断、Claude Code >10K 字符落盘、OpenCode checkpoint 压到 2,000 字符 [外部]；dsh 顺序为 prune→recount→compact [源码] |
| 6 | 成本核算 | 依赖运行时/框架的 cost 字段 | **按官方价目自算**，并把"缓存命中率"当作一等指标（太低要告警） | 账本按 V4-Pro 计价，偏差 6.67× [实测]；Claude Code 把缓存命中率设成告警指标 [外部] |
| 7 | 模型选择 | 默认致远一号 `deepseek-chat` | 关注官方动态：`deepseek-v4-pro` 已路由到 V4.1-Flash 并按 Flash 计费；峰谷价差 2× | 官方新闻页 [官方]；峰谷调度可省一半 |

## 6. 缺口与待验证

1. **中文/校园场景的分布级 token 数据缺失** [外部]：本机数据是单机样本（1 个用户、DeepSeek Flash），不能代表全体用户；建议在 sjtu-agent 里埋点统计（每轮上下文、折叠次数、缓存命中），两周后再校准第 1 条建议。
2. **折叠阈值与"质量下降"的定量关系没有硬数据**：外部只有"context rot"定性说法与无方法学的 70% 数字；建议用可控实验（同任务在 256K/500K/800K 预算下对比任务成功率）替代直觉。
3. **账本价目表的来源未确认**：我只能从数字反推它按 V4-Pro 计价（6.67× 恒定比值），**未读到它的价目表源码**（本机 checkout 只含 web-app 依赖闭包，未包含用量包本体）。
4. **dsh `tool-result-pruner` 的具体阈值未公开**（剪枝包本体不在本机 checkout 内）[外部]。
5. **未覆盖**：非编码 chat 智能体的每轮 token 拆分、研究型 agent 的分布级数据、分 provider 的长期缓存命中统计 [外部]。
